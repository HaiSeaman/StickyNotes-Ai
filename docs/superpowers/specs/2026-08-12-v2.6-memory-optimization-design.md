# V2.6 性能优化设计：封面缩略图（内存优化）

- 日期：2026-08-12
- 状态：设计待审查
- 范围：内存优化（音乐播放器封面缓存），CPU 优化（后台节流，待验证）

## 1. 背景与目标

V2.6 的目标是降低软件内存与 CPU 占用。实测确认：用户环境（打包版）播放本地 MP3 时任务管理器单条目约 450M，其中大头并非 MP3 播放本身，而是 Electron 多进程基线 + 音乐播放列表（840 首真实数据）的 DOM 与封面位图。

**硬性约束（用户明确要求）：**
- 只做代码/功能层性能优化，**UI 视觉（布局、样式、毛玻璃）一律不改**。
- 收益太小的改动直接放弃。
- 本设计只包含实测验证过收益的改动。

## 2. 基线测量数据（2026-08-12，真实 840 首播放列表，CDP + PowerShell 实测）

Electron 各进程工作集（开发模式）：

| 场景 | main | GPU | renderer | utility×2 | 合计 |
|---|---|---|---|---|---|
| 空闲基线（便签页） | ~138M | ~143M | ~95-212M | ~126M | ~420-620M |
| 进音乐 tab（840 首渲染） | ~158M | ~159M | ~447M | ~126M | ~890M |
| 播放中 | ~170M | ~147M | ~442M | ~126M | ~885M |

**音乐列表渲染增量分解（renderer，对照实验：带封面 vs coverPath 清空）：**

| 贡献项 | 内存 | 说明 |
|---|---|---|
| 封面位图（840 张原图） | **~176-280M** | 封面示例 948KB/张，解码位图 ~4MB/张（约 1000×1000） |
| 列表 DOM（840 item ≈ 5000 节点） | ~60M | renderPlaylist 全量构建 |
| MP3 播放本身（html5 流式） | ~6M | 可忽略，无需优化 |

**结论：封面对位图是最大可优化项。** 播放内核（howler html5:true + musicfile 协议 Range 流式）已是正确实现，不动。

## 3. 方案①：封面缩略图（批准实施）

### 3.1 现状
- 主进程 `music:read-metadata`（`src/main/ipc/index.ts`）用 `music-metadata` 提取封面原图（`pic.data`，上限 5MB），sha256 哈希命名存入 `getMusicCoversDir()`（`userData/music/covers/`），`coverPath` 存原图完整路径。
- 渲染层列表项（`musicTab.ts renderPlaylist`）`img.src = musicfile://cover/<coverPath>` 直接加载**原图**。
- 音乐 tab 激活时增量扫描会重新解析元数据（`musicTab.ts:1030`），已有封面会命中 `covers/<hash>` 已存在判断而跳过重写。

### 3.2 改动设计

**主进程（`src/main/ipc/index.ts` music:read-metadata）：**
1. 提取封面后，在写原图的同时生成 96×96 缩略图：
   - `nativeImage.createFromBuffer(pic.data).resize({ width: 96, height: 96, quality: 'good' }).toJPEG(85)`
   - 保存到 `getMusicCoversDir()/thumb/<hash>.jpg`（与原图同 hash，不同子目录）。
2. 返回值 `metadata` 新增字段 `thumbPath`（缩略图完整路径）。`coverPath` 保持原图路径不变（控制条「正在播放」大封面继续用原图）。

**协议层（`src/main/main.ts` musicfile handler）：**
- 无需改动。缩略图位于 `covers/thumb/` 下，现有校验 `realPath.startsWith(getMusicCoversDir() + path.sep)` 天然放行；MIME 由 `path.extname` 映射（.jpg）。

**渲染层（`src/renderer/tabs/musicTab.ts`）：**
- `renderPlaylist` 列表项封面改用缩略图 URL：`buildCoverUrl(t.thumbPath || fallbackToCover(t.coverPath))`。
- 兼容旧数据（无 thumbPath）：`onerror` 时回退加载原图 `musicfile://cover/<coverPath>`（现有 onerror 已存在，扩展为两级回退：thumb → 原图 → 默认 SVG）。
- 控制条封面（`updateNowPlaying`）保持使用 `coverPath` 原图，不动。

**补齐已有封面缩略图（关键兼容步骤）：**
- 新增 IPC `music:ensure-thumbs`：扫描 `covers/` 下原图，为缺失的 `covers/thumb/<hash>.jpg` 批量生成（nativeImage 批量 resize，790 张预估 <10s）。
- 调用时机：渲染进程进入音乐 tab 时后台触发一次（`musicTab` init 后 fire-and-forget），幂等（已存在跳过）。
- 视觉无变化：生成期间列表项缩略图缺失时由 onerror 回退原图，界面不出现空白。

### 3.3 预期收益
- 解码位图：~4MB/张 → ~37KB/张（96×96 RGBA），约 **100 倍缩小**。
- 首屏 + 全滚动场景合计省 **~176-280M**（renderer），打包版任务管理器单条目 450M → ~300M 量级。
- 磁盘：790 张缩略图约 3-8MB（可接受）。

### 3.4 风险
- 低。改动集中在封面生成与列表 URL 选择；原图路径与协议逻辑不动。
- `nativeImage` 在无头/CI 环境的可用性：仅打包版运行路径使用，Windows 桌面环境正常。

## 4. 方案③：后台节流修复（先验证再定）

### 4.1 现状
- 主窗口 `buildWindowOptions` 设置 `backgroundThrottling: false`（`src/main/main.ts:189`），导致窗口最小化/隐藏到托盘时渲染进程定时器全速运行：时钟 1s、闹钟检查 1s、日志 flush 2s、计时器 250ms、音乐进度 250ms。

### 4.2 改动设计
- 删除 `backgroundThrottling: false`（恢复 Electron 默认 true）。

### 4.3 验证清单（实施后必须验证，通过才保留）
1. **闹钟准时性**：最小化/隐藏窗口后设 1 分钟后的闹钟，验证响铃延迟。若延迟明显（节流到 1 次/分钟），回退该改动，或改为方案 4.4。
2. **音乐后台播放**：最小化后音乐是否继续播放（Chromium 对播放音频的页面解除节流，预期正常）。
3. **时钟显示**：恢复窗口后时钟是否正确（预期正常，节流只影响不可见期间）。

### 4.4 备选方案（若 4.3-1 失败）
主进程侧闹钟兜底：main 进程 `setInterval` 检查日历闹钟（`calendar.json`），到点 IPC 通知 renderer 响铃。改动更大，仅验证失败时启用。

## 5. 方案②：播放列表虚拟滚动（未批准，后续可选）

- 840 项只渲染视口 ~40 项，省 ~55M DOM + 提升滚动流畅度。
- 用户本轮未批准。若①实施后仍需进一步降内存，作为后续独立迭代（涉及拖拽排序/自动定位/过滤索引映射，风险中等）。

## 6. 成功标准（可量化）

| 指标 | 基线（实测） | 目标 |
|---|---|---|
| renderer 内存（音乐 tab，840 首） | 447M | ≤ 320M |
| 任务管理器单条目（打包版） | ~450M | ≤ ~330M |
| UI 视觉 | — | 零变化 |
| 闹钟准时性（③） | 准时 | 与现状一致 |

## 7. 非目标 / 明确不做

- 不改任何 CSS 视觉效果、布局、DOM 结构（毛玻璃全部保留）。
- 不做多窗口架构拆分、不换 Tauri、不重写播放内核。
- 不做收益无法量化的激进改动（如 Chromium feature 开关微调）。

## 8. 验证方法

- 复用基线测量脚本（CDP + PowerShell 工作集采集）：①实施前后对比 renderer 内存。
- ③验证清单见 4.3。
- 回归：`npm run typecheck`、`npm test`、手动播放/切歌/收藏/拖拽排序。
